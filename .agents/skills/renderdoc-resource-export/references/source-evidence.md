# Source evidence contract

Collect source evidence before choosing a converter or target representation.
The evidence must describe what the selected EID consumed, not what a resource
name or common engine convention suggests it consumed.

## Exact source identity

Bind all evidence and artifacts to:

- capture identity and immutable capture hash when available;
- replay session identity;
- EID, draw/dispatch identity, API, queue, and pipeline identity;
- shader stage, entry point, encoding, and raw shader hash;
- resource IDs, subresources, views, bindings, and relevant byte ranges;
- the request hash covering source scope, target profile, dependency policy,
  coordinate profile, and requested output classes.

Re-check this identity before preparation, finalization, and validation. A UI
selection change is not authorization to retarget an in-progress export.

## Mesh and draw evidence

Record the primitive topology and whether the draw is indexed, indirect,
instanced, tessellated, geometry-expanded, mesh-shader generated, or otherwise
not representable as a conventional input mesh.

For each index stream, record:

- resource ID, byte offset, format, first index, index count, and restart value;
- base vertex, vertex offset, and any draw argument or indirect argument range;
- the resolved referenced range and out-of-range or unavailable reads.

For every vertex shader or mesh input, record:

- semantic name and index or API location;
- shader scalar/vector type and component count;
- input slot, source resource, byte offset, stride, and element offset;
- source format, component type, normalization, packing, and endianness;
- per-vertex or per-instance rate and instance step divisor;
- decoded count/range and source byte hash;
- destination channel or sidecar mapping selected later.

Preserve all observed inputs, including positions, normals, tangents, colors,
blend indices and weights, multiple UV sets, instance transforms, and custom
attributes. Do not drop an input because FBX, glTF, Unity, or Blender lacks a
directly named channel. Use a target-supported custom stream or a lossless
sidecar and record the mapping.

Distinguish data absent from the input assembler from data generated by a
shader, tessellator, geometry stage, mesh stage, skinning stage, or procedural
calculation. If only post-transform geometry is available, label it as such;
do not claim that it is the original authored mesh or rig.

## Texture, view, and sampler evidence

For every sampled, loaded, read-write, or attachment texture needed by the
requested result, record:

- resource ID, binding, shader stage, dimension, width, height, depth, array
  size, mip count, plane count, and sample count;
- selected mip, slice, face, plane, sample, and byte/content hash;
- resource format and the actual bound view format;
- channel order, swizzle, signedness, normalization, compression, and alpha
  interpretation when observed;
- whether sampling is sRGB-decoded, linear, integer, depth/compare, or unknown;
- sampler filter, min/mag/mip behavior, address modes, anisotropy, comparison
  function, border color, LOD bias, and min/max LOD;
- shader operations that alter coordinates, derivatives, mip choice, compare
  behavior, or sampled channels.

Color space follows the bound view and observed shader use, not a filename.
Record both the stored encoding and sampling interpretation. If a typeless
resource has multiple views, preserve the view used by the selected draw.
Do not flatten arrays, cubemaps, volume textures, MSAA textures, depth textures,
or multiple relevant mips without an explicit target mapping or recorded loss.

## CBuffer and material evidence

For every relevant constant block or push/root constant range, preserve:

- API binding and resource/range identity;
- raw bytes and byte hash;
- variable path, declared type, scalar kind, rows, columns, array count, byte
  offset, byte size, packing, and row-major or column-major layout;
- the live decoded value at the selected EID;
- shader reads and the calculation or output influenced by the value;
- classification as `material`, `system`, or `unknown`, with evidence.

Material classification requires observed shader use plus a stable role such as
base color, normal scale, roughness, metallic, emissive, opacity, cutoff, or a
shader-specific exposed parameter. Names alone are supporting evidence, not
proof.

System values include camera/view/projection matrices, object transforms,
viewport or render-target dimensions, time, frame index, exposure, and other
engine-owned state. Map these to target-native values where possible. Do not
bake the captured value into a reusable material. Keep ambiguous values as
unknown parameters rather than forcing a material or system classification.

## Shader and dependency evidence

Shader evidence must identify the exact stage, entry point, original encoding,
raw hash, input/output interface, live bindings, CBuffer layout, resource
operations, branches, and output writes. A target conversion must cite the
admitted shader analysis or route result it consumed.

Inspect frame flow when the draw:

- reads a GBuffer, depth pyramid, history buffer, shadow atlas, scene color, or
  another earlier pass output;
- produces attachments consumed by later lighting or composition draws;
- relies on blending with pre-existing target content;
- uses UAV, feedback, indirect, or cross-draw data that cannot be represented
  by a standalone material.

For each dependency, record producer and consumer EIDs, resource/subresource,
access type, required value or semantic, and whether it is included, replaced
by a target-native service, approximated, or intentionally dropped. Separate
observed facts from inferred pass semantics.

## Evidence sufficiency

Source evidence is sufficient only when every requested output has an exact
source or an explicit bounded unknown. Use these states:

- `observed`: directly supported by capture evidence;
- `derived`: deterministically computed from observed evidence, with method;
- `inferred`: likely semantic interpretation, labeled with rationale;
- `unavailable`: capture or target cannot supply it;
- `conflicting`: evidence disagrees and requires resolution.

Never fill an unavailable vertex component, texture interpretation, CBuffer
field, or dependency with a conventional default without recording that the
output is an approximation and obtaining authority when it changes visible
results.
