# Bread 1.13.24：着色器恢复与完整源码整理

## 现场与原因

本次现场来自应用 PID 38068、捕获 `白银之城/6.rdc`、项目 `ReplayLab Project`。20:05:56–20:11:22 的恢复共 326.6 秒，三个着色器中两个已替换，一个因 `DXIL access evidence unavailable after bounded recheck` 失败。

失败工作区 `d2e9720e…` 的原始 DXIL、反汇编及工具执行记录都在。`workspace.py` 错把原始反编译作业的输出 HLSL 摘要要求为当前可编辑 HLSL 的摘要；项目导入或用户整理后两者自然不同，导致原始 DXIL 证据被错误排除。修复移除这项错误耦合，仍检查原始字节码、反汇编摘要、唯一作业记录和固定工具。候选编译输出的严格内容检查不变。

旧项目记录还把当前源码退回 `52f91101…`，但第 21 版完整源码 `b5326791…` 及候选字节码 `48160f1f…` 都保存在工作区。已在工作区锁内核对当前内容及 revision 21 记录，备份旧文件到 `ai/recovery/20261013-restore-regression/`，原子恢复该版源码，未手改 manifest。随后通过正式 `register_active_project_workspace` 接口将它注册为项目 head generation 14，knowledge `ce98204803ff3306afac937eb8878782`。这是恢复最新已验证版本，不表示该版已完成用户要求的全部可读性整理。

启动阶段的两个 `get_shared_shader_replacements` 错误属于只读库存查询发生在 catalog 尚未初始化时。现在无相关 native 替换记录的初始化状态返回 `catalogReady=false` 和空库存；已有记录与身份不匹配仍报错，写入操作的身份检查不放宽。

## 恢复路径

- 在导入旧项目源码之前检查已有工作区。当前源码若对应本地已通过验证的候选，则复用该候选，再按正常当前捕获检查应用；不覆盖源码、不重新编译、不将它冒充为旧项目源码。
- 未编译的本地修改保留并给出原因。没有有效候选的修改不能保证应用成功。
- 相同源码的旧 ABI 候选保留原有有界恢复路径；不会因提前检查而截断恢复。
- 使用现有编译字节码、工具证据、Shader 配对验证缓存和整个 RDC 的恢复缓存，不新建重复数据库。

1.13.23 的安装实测确认原失败项（ResourceId 尾号 755）恢复了 revision 21，但发现另一项尾号 723 的注册来源工作区已有未编译草稿。新增保护过早跳过该项，没有继续尝试现有持久快照里的 `eb7340d9…` revision 18。1.13.24 修复这个回归：保留草稿，尝试严格校验过的原成功工作区，再走正常应用；未找到有效工作区才跳过。另修复跳过项重复计入 attempted 的计数错误，维持 `attempted = applied + failed` 的既有协议，界面不再因不一致计数丢弃整个结果。

旧缓存的三个 Python 算法摘要没变，原生 `renderdoc.dll` 摘要从 `6ad9a103…` 变为 `36ae7ef4…`，因此上次升级后按设计重新验证。当前版本没有再改变该原生库。GPU 资源与替换句柄属于新 replay 进程，仍需重新创建，不能直接复用上次进程的句柄。旧现场的两个成功项已复用字节码，不能把全部耗时称作重新编译。

## 整理流程

Skill 与交付工具一致要求：取得完整文件，映射计算分支及依赖，在同一副本完成全部请求范围，整体自检，集中修复，然后最终编译、验证、应用。自检关注可读性、类似 Unity 的计算结构、函数接口和冗余中间变量，仍保留原 Shader 的语言、接口和运算约束。

`finish_shader_workspace_organization` 的最终验证/应用要求当前源码摘要对应完整 Agent 源码自检；未完成或过期返回 `source-review-pending`，不产生编译或应用。显式 `publication_mode=checkpoint` 可用于中间技术诊断，保持同一草稿可写；最终验证失败也保留原草稿。评审到执行之间再次核对源码摘要，避免应用另一份内容。源码自检不依赖预先编译，实际交付后的任务完成检查独立进行，不构成循环依赖。底层编译工具仍可用于必要诊断，未添加机械的迭代次数限制。

## GUI 卡顿的直接证据

安装实测中的单次 `get_capture_status` 耗时 7.54 秒，Bridge 的 `mailboxAgeAtClaimMs` 为 7547、`pollGapMs` 为 7860，而 worker、UI transaction 和 replay 耗时均近零。关闭测试脚本的 Python 调试跟踪后仍复现约 6 秒的同类等待，不能归因于编译或请求处理。

5 秒间隔的 Python 全线程栈持续定位到 GUI 定时回调：`ShaderConsolePanel._flush_filesystem_changes → refresh → load_console_snapshot → _workspace_model → _validate_editable_source_gate → _load_project_shader_library → _validate_replay_project`。控制台只为显示状态，却在 GUI 同步完整验证项目库，且每个工作区重复做一次。项目变化或 AI 日志变化会不断触发，挤占普通工具请求和计时器。对应原生栈也显示主线程处于 QTimer 调用的深层 Python 执行中，未显示 GPU 等待。

现场证据保存于 `%TEMP%/bread-real-restore-cold-2cnkri0r/`、`%TEMP%/bread-real-restore-warm-gsm6jrsx/`；后者的 `python-stacks.log` 已排除脚本 trace 开销。第一次探针因隐藏窗口的默认退出策略提前结束，未计为恢复结果。后两次 1.13.23 测试是诊断基线，仍为 2 个应用、1 个跳过，不能作为完成交付或缓存命中速度的证明。

修复把控制台的磁盘读取与验证放入单个后台 worker，由 GUI timer 取结果。请求合并，捕获切换和关闭会取消请求、丢弃旧结果；后台不持有 Qt 或捕获控制器。关闭失败不丢弃 worker owner，也不静默继续 Python finalization。首个异步结果仅清理面板创建前有明确时间的旧日志，保留加载期间新产生的错误。

同一快照只完整验证一次项目库；显示缓存命中仍安全读取并校验所有依赖的内容摘要，metadata 只用作提前失效判断，源码打开/保存的严格验证入口不使用显示缓存。真实项目 56 个知识文档、7 个工作区的离线测量：旧快照 4.44 秒、6 次全库验证；新首次 1.03 秒、1 次验证；新重复读取 0.181 秒、0 次完整验证，仍核对 163 个依赖文件。
