# Shader 工作区语义导航与资产匹配复核

首次修复版本：Bread runtime 1.13.38；本次追加已安装 1.13.39，Shader workbench Skill 98、资产调查 Skill 28。

## 1. F12 的实际问题与修改

之前存在 LSP 接口，但安装中没有可用的语义服务，部分定位仍走轻量本地索引。现在随 x64 应用安装固定版本的 Slang 2026.20 语言服务，以编译器语义处理 HLSL 定义、重载、局部遮蔽、结构体成员和 include；文档 URI、声明范围及未保存的文档版本共同确定定位身份。迟到结果不覆盖新请求，初始化及查询可超时、可取消。语言服务返回空结果时不再按名字跳往别的 Shader。

这与 VS Code 的 language provider / LSP 分工一致。嵌入 VS Code 或 Monaco 编辑控件本身并不会提供 HLSL 语义，仍需要语言后端。保留现有 Qt 编辑器可避免额外引入 Electron/WebView 的资源与生命周期负担。

Slang 没有原生 references API。目前“查找引用”先在当前编译单元已打开文档中收集候选，再逐一由编译器确认是否指向同一个完整声明身份；候选名字相同不会直接算作引用。该查询有数量/时间上限、版本缓存和取消机制，尚不等于搜索所有未打开文件。HLSL 实际语言服务测试 8/8；包括预览文件在内的最终 Qt 编辑器测试 16/16。

另直接读取本次用户保存的 151,210 字节 Shader，抽取 16 个真实函数调用交给 Slang 定位，16/16 指向正确声明；本机首次约 95 ms，其余约 5–15 ms。这是当前文件的语义服务实测，不代表所有 Shader 或完整 UI 响应时间保证。

## 2. 可编辑文档与 include

可恢复的 HLSL/GLSL 源码、反编译源码和未通过编译的源码都可以作为工作副本编辑；能否编辑与能否应用到回放分开判断。历史快照/外部原始文件保留不变，编辑发生在工作副本。

include 只沿当前编译单元明确的文件引用解析，不搜索其他 Shader 的同名文件。导航可以异步打开对应文档。头文件使用独立内容版本保存，外部头文件的第一次保存生成受管理副本并更新确切引用；有未保存父文档时保留用户缓冲，不悄悄覆盖。编译冻结完整依赖输入，主文件和头文件的内容身份一起控制候选复用。仅头文件变化也会使旧编译/应用结果失效，项目恢复不能把新头文件当作旧的已验证版本应用。

AI 预览仍保留真实文件 URI 和保存身份；只在发送给语言服务的文本里，将明确的相对 include 投影到主源码目录的绝对路径。这样不用在 source 目录创建占位 Shader，也不改变编辑器缓冲或保存内容。预览和正式源码的未保存修改互不覆盖。

此处的依赖收集有明确边界：固定 include、简单确定条件及受支持宏表达式；它不是另一个完整 HLSL 预处理器。复杂、无法确定的引用会给出具体诊断，不能猜路径；这种诊断不应让主源码失去编辑能力。

## 3. f28 任务中为什么没有找到名称

任务 `f28b8649dd82473b8c99e24e3e919558` 的目录索引有 702,116 条延迟读取记录，只有 8 个解析包、62 条数值索引记录、0 张纹理缩略图。目录枚举“完成”不等于资源内容已经参与比对。捕获中已有 11 张可用纹理指纹，原任务却没有解码候选材质的 6 张引用纹理。

`MI_MuninDefault_C_Body01_A` 的原始 0.98 排名主要来自少量数值命中；其中一些在 View 块，材质块中只有短数值片段，并无完整身份链接。已读取的父链是 `MI_MuninDefault_C_Body01_A → MIT_CharacterPBR → M_CharacterPBR`。父材质 SM6 变体的已解码输出，在原声明偏移处仍不匹配捕获。两个颜色值虽在其他位置出现，不能直接把整套变量名平移过去。

本轮实际解码了这 6 张纹理并入库，约 136.64 秒。与捕获中 9 张非纯色纹理比较，最小感知距离分别为 BaseMap 24、Lighting Blend Mask 21、MRA 14、Normal 23、Wet Mask 23、Drip 22，均未达到现有 ≤12 阈值。MRA 最近的对象是 BC5 法线纹理，颜色差也很大。结论是“当前纹理证据不支持该候选”，不是证明游戏资产里不存在对应材质。BC5 蓝通道重建与捕获表现不同，也意味着不能仅凭那一张法线图绝对排除候选。

完整实际读取得到的证据保存在系统临时目录 `bread-munin-texture-validation.json`；本轮没有借此改写任何用户 Shader 或发布猜测的别名。

## 4. 已修改的资产链路

- 将文件名覆盖、实际内容覆盖、纹理/网格/数值证据分别报告；数值候选分数不再冒充已确认身份。
- `uex_preview_texture` 成功后自动把源文件/伴随文件、reader 配置和输出 PNG 的身份绑定到原资产索引；之后可复用，不必再次解码。
- 自动将 Unreal `/Game/.../Texture.Texture` 对象引用解析为 reader mount 下的确切 `.uasset` 路径。实测原格式会产生 Asset not found，规范化后读取成功。
- 对明确选取的 reader 预览支持普通 2K/4K 图像，保留独立字节/像素限制；不扩大日常目录索引的读取预算。
- 数值检索保留特殊值线索；候选布局比较新增完整连续 float32 窗口，包含 `1,0,1,0.5`。记录实际字节偏移、寄存器通道、重复/移位情况；不跨 CBuffer 或未知空洞拼接，不自动把移位命中变成别名。
- Skill 在大范围代码整理前要求按绑定纹理/网格 → 依赖与引用 → 材质实例/父链 → 当前平台编译布局调查。缺少缩略图应补读候选，不应据此认定匹配失败；当前有效映射可以复用。

## 5. 平台与后处理

CBuffer 应依据捕获反射、实际编译平台与 permutation、实例覆盖及编译后的字段偏移处理。标量可以占用同一个 float4 的不同通道；数组步长、矩阵主序、整数/布尔表示、SPIR-V 布局选项都会影响布局。参数列表顺序和相同游戏版本不能替代这些数据。

后处理和 global Shader 常使用运行时 RenderTarget，没有可对应的解包纹理或网格。此时优先使用可获取的可执行代码/Shader archive 身份、平台变体、Pass 输入输出和资源签名，再缩小名称搜索范围。不要强行套用普通 Mesh → Material 的路线。

同版本通常提高匹配机会，但符号剥离、共享 Shader、多种材质实例、运行时参数以及动态生成资源仍会造成无法唯一恢复原始名字的情况。已支持字段继续命名，剩余字段保留准确的物理位置与中性算法名称，不因此停止源码整理。

## 6. 仍然明确存在的边界

1.13.38 的 UEX CLI 每次 preview 都重新挂载目录，实际每张约 20 秒。这个耗时点已在下述 1.13.39 追加修复中接入持久 reader；首次挂载成本仍然存在。

本轮改善语义编辑及资产调查机制，没有宣称已恢复全部原始名称，也没有把之前数值验证未通过的 Shader 宣称为通过。

## 1.13.39 追加修复：可执行交付、少量锚点与读取复用

用户要求的是生成可保存、可编译、可替换的工作区源码。之前的 `finish(apply_shared_resource=true, validate_for_apply=false)` 可绕过数值比较；替换或显示失败时顶层还可能沿用保存成功。现在 final 默认集中验证，apply 无法通过关闭验证标记绕过；保存成功、验证成功、替换成功、显示成功分别记录，任何请求的交付步骤失败不能报告完成。

普通反编译默认检查生成源码的编译、ABI 和捕获输出，不永久替换，除非请求 apply。对照使用捕获原始二进制，不能拿两份相同的重编译源码自比。修复 include、声明、接口或数值问题后，通过 `validate_shader_workspace_delivery` 检查当前源码，无须重新反编译。独立参考反编译与显式草稿保存保持低成本；草稿可编辑，但不能当成已通过交付。这个修改不会让每个中间编辑都触发编译。Skill 98 保留先完成全文件组织和源码自检、再集中物理验证的顺序。

资产调查先选少量有辨识度的内容锚点，再沿索引中的依赖与反向引用寻找材质、父资产和 Shader。匹配所有纹理不是前提，未知的场景贴图、默认纹理或动态 RenderTarget 不会否定已建立的具体链接。通用关系层不依赖引擎/API；引擎适配器提供真实资产边，平台适配器解释实际布局。目录邻居仅为待读取线索，数值或关系路径的排名不冒充物理身份。尚未支持的格式仍明确报告覆盖缺口。

UEX 对精确 loose package 的 preview/preview-texture 改用 JSON-lines 常驻进程，在同一 Host 中复用挂载。只保留一个进程，空闲 5 分钟释放，Host 退出时回收。配置、profile、程序/DLL、usmap、已读取包及伴随文件改变会使挂载失效；解码期间输入变化也拒绝登记结果。请求可取消、有超时，崩溃后的下一次调用重建进程，其他 reader 保留现有 CLI 路线。

对 `E:\SilverPalace_Unpacked\raw` 的实际测试如下；数据来自 `bread-uex-persistent-benchmark.json`，四次使用同一 reader PID，全部输出入库，未修改 Shader 或别名：

| 读取 | reader 耗时 | 含指纹/入库总耗时 |
| --- | ---: | ---: |
| 第一次 Drip，冷挂载 | 20.016 秒 | 20.907 秒 |
| 新 Body_D，复用挂载 | 0.421 秒 | 6.031 秒 |
| 新 MRA，复用挂载 | 0.140 秒 | 1.953 秒 |
| 再次 Drip | 0.031 秒 | 0.906 秒 |

这消除了逐图约 20 秒的重复挂载。高分辨率 PNG 指纹计算仍有 CPU 成本；Host 结束后的下一次首次读取仍需挂载，已登记且输入不变的内容指纹可以跨任务复用。
