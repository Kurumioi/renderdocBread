# 检查点保留决策：快速 A/B（2026-09-09）

使用已验收的 stage-v22 独立二进制，没有重新构建或加入未验收实验。
同一捕获在同一进程内开启/关闭检查点，其他优化不变；两组都去掉第一轮，取后续三次
SetFrameEvent 耗时中位数。像素读回不计入该耗时，全部绑定颜色/深度输出与独立强制回放一致。
测试开始、过程及结束检查未发现其他 RenderDoc GUI 回放进程。这是快速小样本，非屏幕显示延迟。

| 捕获 / EID | 关闭检查点 | 开启检查点 | 时间减少 |
|---|---:|---:|---:|
| 1.rdc / 24917 | 254.17 ms | 223.22 ms | 12.2% |
| 1.rdc / 29385 | 244.39 ms | 212.41 ms | 13.1% |
| 6.rdc / 5489 | 69.23 ms | 59.33 ms | 14.3% |
| 6.rdc / 12016 | 113.05 ms | 109.99 ms | 2.7% |

两捕获分别有 11 次实际检查点命中，原生点分别为 7690、2070。报告的额外存储分别
61,329,408 B（58.49 MiB）、118,484,992 B（113 MiB），其中包含 CPU 描述符记录等元数据，
不是纯 GPU 分配。共享引用字节不应再次算成新增显存。第一次 save 原生日志分别约 449.76 ms
和 11.24 ms，未计入上表热切换；后续重建成本不能据此一次值推定。

6.rdc 的 512 MiB 配置首轮被预算预估拒绝，没有实际命中，不作为速度 A/B。补测把预算
放宽为 1 GiB 后命中，但实际保存只有 113 MiB。configure 记录完整描述符估算 523,321,344 B，
save 实际只保存 913,408 B 描述符差异，存在准入估算过于保守的问题；并非实际需要 1 GiB 快照。
本轮只测试和记录，没有修改该预算逻辑。

结论：检查点在所测位置有 3%–14% 的有限收益，尚不支持为了实时拖动而继续全面扩张。
额外存储没有达到数 GB；主要问题是命中后仍重放较长前缀、搬运大量初值。可以将其保留为可关闭
的辅助优化，优先保留独立有效的向前增量、静态资源过滤和界面调度。

## 之前 6.rdc 的速度来自什么

- 最早约 5–9 ms 的反向预览全部是 `ScrubSnapshotHit`，`replay_ms=0`，显示 GPU 截图缓存，
  并延迟提交真实 EID。这条路径随后按照用户要求移除，不能把其时间当作真实检查点重绘。
  原记录：主工程 `output/eid-performance-20260905/performance-findings.md` 第 4、8、173 行。
- 后续真实回放包括 CPU 源初值的 GPU 本地副本、跳过不变资源、减少等待/目标命令处理，以及
  合并过期拖动请求、修正当前图像/面板发布；这些不全依赖检查点。
- 以前同版本 v7b 的 6.rdc 检查点 A/B 也只有早段约 49→42 ms、晚段约 81→78 ms，
  与这次有限收益方向一致。不同构建/机器状态的绝对耗时不作版本回归结论。
- 合法向前增量属于另一条保留当前工作状态、只执行新增命令的路径；此前 1.rdc 已有
  约 193→2.5–2.9 ms 的受控正例，但往回和不安全区间不能获得同样收益。
